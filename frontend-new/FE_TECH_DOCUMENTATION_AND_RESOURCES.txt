PROJECT FRONTEND TECHNOLOGY STRATEGY & LITERATURE REVIEW
======================================================
Based on "React 19 in Practice" (Nelson, 2025), "Micro Frontends Architecture" (Da Silva, 2025), and related contemporary literature.

## 1. Core Architectural Shift: The "Full-Stack Frontend"
**Source**: *React 19 in Practice* by Ted E. Nelson (Dec 2025)

The primary strategic shift for our Frontend Engineering (FE) is the move from a pure "Client-Side SPA" mindset to a "Full-Stack Frontend" architecture.

### 1.1 Key Technical Implementation Details
- **Server Components (RSC)**: Adoption of Server Components to move data fetching logic to the server, reducing client bundle size and shifting the "mental model" of where code runs.
  - *Recommendation*: Identify "Leaf Components" (pure display) vs. "Interactive Components". Move leaf components to server rendering where possible.
- **The React Compiler**: 
  - *Instruction*: Stop manual performance tuning with `useMemo` and `useCallback`. The project config must enable the React Compiler to handle memoization automatically.
  - *Goal*: "Native JavaScript" feel, removing the overhead of dependency array management.
- **Server Actions**:
  - *Change*: Replace client-side API calls inside `onSubmit` handlers with **Server Actions**.
  - *Pattern*: Pass async functions directly to the `<form action={fn}>` prop. React handles the lifecycle (pending, error, success) automatically.
- **"Zero Latency" Interface**:
  - *Technique*: Aggressively use `useOptimistic` to update the UI *before* the server responds. 
  - *Implementation*: User clicks "Rename" -> UI updates immediately -> Server Action runs in background -> UI reconciles if error occurs.

## 2. Scalability Architecture: Micro-Frontends & DDD
**Source**: *Micro Frontends Architecture for Scalable Applications* by Vanderlei Alves da Silva (July 2025) & *Building Micro-Frontends* by Luca Mezzalira (2nd Ed)

As the application grows, we will avoid "Separation by Type" (e.g., all components in one folder) and adopt "Separation by Domain".

### 2.1 Domain-Driven Design (DDD)
- **Structure**: The codebase must be organized around Business Domains (e.g., `features/mining-engine`, `features/user-access`), not technical layers.
- **Decentralized Governance**: Each "feature" acts as an independent mini-application with its own public API (`index.ts`). Internal implementation details (components, helpers) must not leak to other domains.

### 2.2 Micro-Frontend Integration Patterns
- **Container Application (The Shell)**: A lightweight capability that hosts the navigation and global context (Auth, Theme).
- **Communication**: Use an Event Bus or specific Cross-Application Communication pattern for loose coupling between domains, rather than shared global state (Redux).
- **Fast Flow > Reusability**: Favor duplicating a small utility function inside a domain over creating a tightly coupled "shared-utils" library that blocks independent deployment (Mezzalira's core advice).

## 3. The Modern Toolchain & TypeScript
**Source**: *Full-Stack React TypeScript* by Julien Park (Nov 2025) & *Learn React with TypeScript* by Carl Rippon (3rd Ed)

### 3.1 The "Golden Stack" for 2025
- **Build**: Vite 6.x (Instant HMR).
- **State/Fetching**: TanStack Query v5+.
  - *Reason*: Manages "Server State" (caching, deduping) effectively, freeing React to handle "UI State".
- **Validation**: Zod.
  - *Implementation*: Share Zod schemas between Backend (if Node) or generate TypeScript types from Backend (if Python) to ensure a "Type-Safe Contract".
- **Testing**: Vitest + React Testing Library.
  - *Focus*: Test user interactions (clicks, text entry), not implementation details.

### 3.2 Advanced Hooks
- **useActionState**: To manage the complex state of form submissions (pending, errors, return values) without `useState` boilerplate.
- **useFormStatus**: To disable submit buttons deep in the component tree without prop drilling `isSubmitting`.

## 4. Infrastructure & "AI-Ready" Operations
**Source**: *Modernizing Core Infrastructure for AI-Ready SaaS Applications* by Lee Atchison

### 4.1 "XOps" & Observability
- **Observability is King**: It is insufficient to just log errors. We must log *behavior*.
- **Implementation**:
  - Every "Server Action" must emit structured logs.
  - Frontend must report "Interaction to Next Paint" (INP) real-time metrics to the centralized observability platform.
- **AI Readiness**: The infrastructure must support "Auto-Scaling" not just for traffic, but for "Training/Inference" bursts if local AI models are integrated into the React frontend.
