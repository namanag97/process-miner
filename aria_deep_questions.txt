Q1: THE DUAL-LOG IDENTITY CRISIS
--------------------------------------------------------------------------------
File: backend/src/models/orm.py (EventLog + OCELLog)
File: backend/src/models/ocel2.py (OCEL 2.0 models)
File: backend/src/services/ingestion.py (populates only EventLog)

Observation:
  The system defines TWO distinct log representations:
  - EventLog → ProcessCase → ProcessEvent (case-centric, 1:N hierarchy)
  - OCELLog → OCELObjectType → OCELEvent → OCELObject (object-centric, M:N)

  However, IngestionService ONLY populates the case-centric EventLog.
  The OCEL2 tables exist but are never written to during standard ingestion.

Question:
  If a customer uploads an OCEL 2.0 file (JSON/SQLite), which ingestion 
  path handles it? Does the system correctly detect the format and route 
  to the appropriate ORM models, or does it force-flatten OCEL data into 
  the case-centric structure?

Why This Matters:
  OCEL 2.0 research (vdaalst.com) emphasizes that flattening object-centric 
  data destroys convergence semantics. If we're claiming OCEL support but 
  silently converting to EventLog, we're creating "Feature Theater" — the 
  schema exists for marketing, not mining.

Hypothesis:
  The OCEL2 models were added as forward-looking scaffolding. The actual 
  integration (OCEL file detection → OCEL table population → OCEL-native 
  algorithms) is incomplete. This creates an "Ontological Rift" where the 
  data model promises more than the runtime delivers.

Severity: CRITICAL (Semantic Misrepresentation)

Q2: THE PROCESSCASE IDENTITY PARADOX
--------------------------------------------------------------------------------
File: backend/src/models/orm.py (lines 118-144)
File: docs/ONTOLOGY_SUMMARY.md (ProcessCase section)

Observation:
  ProcessCase has:
  - `id`: UUID (internal primary key)
  - `case_id`: String(255) (external case identifier from source)
  - `log_id`: FK to EventLog

  The ONTOLOGY_SUMMARY recommends a "composite key (log_id + source case_id)".
  However, the ORM defines `case_id` as a simple indexed column, not part 
  of a unique constraint with `log_id`.

Question:
  If two different EventLogs contain cases with the same external `case_id` 
  (e.g., both have "Case-001"), does the system correctly isolate them, or 
  can queries conflate cases across logs?

  More critically: When filtering a log (creating a derived EventLog with 
  is_filtered=true), do the new ProcessCases get fresh UUIDs or are they 
  copied? If copied, does `source_log_id` correctly trace lineage?

Why This Matters:
  jQuery taught us: "Consistency in naming and behavior reduces learning 
  curve." If `case_id` means different things in different contexts 
  (globally unique vs. log-scoped), it's a naming violation that will 
  confuse every developer who touches the model.

Hypothesis:
  The current design implicitly assumes `case_id` uniqueness within a log 
  but doesn't enforce it at the database level. This is a latent integrity 
  bug waiting for a multi-log merge or cross-log query.

Severity: HIGH (Data Integrity Risk)

  "Anemic Domain Model" anti-pattern where entities are data containers 
  without behavior or rich attributes.

Q4: THE DUCKDB → ORM HANDOFF GAP
--------------------------------------------------------------------------------
File: backend/src/services/duckdb_ingestion.py (parse_csv_fast returns Arrow)
File: backend/src/services/ingestion.py (ingest_file creates ORM objects)
File: backend/src/api/routers/processes.py (upload_process endpoint)

Observation:
  The upload flow does:
  1. DuckDBIngestionService.parse_csv_fast() → Returns Arrow tables + stats
  2. IngestionService.ingest_file() → Still iterates Python loops to create ORM

  The Arrow table returned by DuckDB is essentially DISCARDED. We only use 
  the precomputed statistics. The actual event data is re-parsed by the 
  standard ingestion path.

Question:
  Why are we paying the "Parse Tax" twice? DuckDB already vectorized the 
  CSV into columnar Arrow format. Why does IngestionService then iterate 
  row-by-row with Python loops to create ProcessEvent objects?

  Shouldn't there be a direct Arrow → Database bulk insert path that 
  bypasses Python object allocation entirely?

Why This Matters:
  Research on DuckDB/Arrow (duckdb.org) emphasizes zero-copy as the key 
  performance benefit. We claim "10x faster ingestion with DuckDB" but 
  the actual data still flows through Python's slow object model.

Hypothesis:
  DuckDB was added as a "speed demo" for column detection and statistics, 
  but the core data path was never refactored. This is "Performance 
  Theater" — the fast tool is present but not integrated into the 
  critical path.

Severity: HIGH (Performance Lie)

Q5: THE ANALYTICSCACHE STALE DATA TRAP
--------------------------------------------------------------------------------
File: backend/src/models/orm.py (AnalyticsCache model)
File: backend/src/services/analytics.py (no cache usage)

Observation:
  AnalyticsCache exists in the ORM with:
  - analysis_type
  - result_json
  - created_at / expires_at

  Yet the AnalyticsService methods (detect_bottlenecks, analyze_rework, 
  get_cycle_time, etc.) have NO cache read/write logic. They compute 
  everything fresh on every call.

Question:
  Is AnalyticsCache dead code? If not, what populates it and what reads 
  from it? If it IS used elsewhere, how is cache invalidation handled 
  when the underlying EventLog is modified (e.g., filtered)?

Why This Matters:
  SaaS caching research (moldstud.com) emphasizes that cache invalidation 
  is "the hard problem." Having a cache table with no clear invalidation 
  strategy is worse than having no cache — it's a stale data timebomb.

Hypothesis:
  AnalyticsCache was designed as infrastructure but never wired up. Every 
  analytics call pays full compute cost, and when caching IS added later, 
  the invalidation logic will be an afterthought, leading to "Ghost 
  Bottlenecks" (cached results from deleted/modified logs).

Severity: MEDIUM (Performance + Correctness Risk)

Q7: THE EVENTLOG IMPLICIT STATE MACHINE
--------------------------------------------------------------------------------
File: docs/ontology/06-STATE_MACHINES.md (EventLog Processing section)
File: backend/src/models/orm.py (EventLog has no status field)
File: backend/src/services/ingestion.py (creates EventLog atomically)

Observation:
  The State Machine documentation explicitly lists EventLog states:
  - DETECTING (columns)
  - INGESTING (parsing)
  - ACTIVE (ready)
  - FAILED (error)

  But these are IMPLICIT states detected by "presence of data" rather 
  than an explicit `status` field. The documentation even notes:
  "Note: This is an implicit state machine — not stored in a status field"

Question:
  If ingestion fails halfway (10M rows, crashes at row 5M), what state is 
  the EventLog in? The documentation says "FAILED (exception)" but there's 
  no mechanism to mark this. The EventLog might exist with partial cases, 
  and subsequent analytics would run on corrupted data.

  Is there a transaction boundary that ensures atomic creation, or can we 
  have "Zombie Logs" (created but never completed)?

Why This Matters:
  Process mining on incomplete data produces meaningless results. If a log 
  has 50% of its cases, bottleneck analysis is statistically invalid. The 
  user needs to KNOW the log is partial.

Hypothesis:
  The system assumes successful ingestion or complete rollback. In reality, 
  SQLite/PostgreSQL transactions can commit partially, and the async nature 
  of Python might leave dangling records. We need an explicit `status` 
  field with guards that prevent analysis on non-ACTIVE logs.

Severity: CRITICAL (Data Corruption Risk)

Q8: THE WORKFLOWRUN TERMINAL STATE TRAP
--------------------------------------------------------------------------------
File: docs/ontology/06-STATE_MACHINES.md (WorkflowRun states)
File: backend/src/models/orm.py (WorkflowRun model)

Observation:
  WorkflowRun has terminal states: COMPLETED, FAILED
  State transition table shows: "reversibility: never" for both.

Question:
  If a WorkflowRun fails due to a transient error (network timeout, rate 
  limit), can a user retry it? The state machine says FAILED is terminal, 
  meaning the only option is to create a NEW run.

  Is there value in supporting a "RETRY" transition from FAILED → PENDING?
  Or would this violate the immutability principle that makes audit trails 
  reliable?

Why This Matters:
  Enterprise workflows deal with transient failures constantly. Forcing 
  users to create new runs for every retry pollutes the run history and 
  loses the context that "Run #5 was a retry of Run #4."

Hypothesis:
  The current design prioritizes audit trail immutability over operational 
  convenience. This is a valid choice, but should be explicit. An 
  alternative is a "parent_run_id" field that chains retries without 
  mutating the original run's state.

Severity: MEDIUM (UX + Auditability Tradeoff)

Q10: THE STALE-WHILE-REVALIDATE ASSUMPTION
--------------------------------------------------------------------------------
File: frontend-new/src/sdk/hooks/*.ts (useQuery patterns)
Observation from React Query research (ui.dev):

  React Query defaults to `staleTime: 0`, meaning data is immediately stale 
  and refetches on every mount/focus.

Question:
  What staleTime values are used for process mining data? A process map 
  derived from a static EventLog should be "fresh forever" (until the log 
  is modified). Are we wastefully refetching immutable data?

  Conversely, if analytics are cached with long staleTime but the log is 
  deleted, do cache entries become orphaned?

Why This Matters:
  Over-fetching wastes bandwidth and compute. Under-fetching shows stale 
  data. Both hurt user trust. The strategy should be:
  - Static derived data (DFG, variants): Long/infinite staleTime
  - Dynamic mutable data (workflow runs): Short staleTime
  - Data with dependencies: Invalidate on parent change

Hypothesis:
  staleTime is likely defaulted across all queries. A deliberate "Freshness 
  Policy" per data type would reduce API load and improve perceived speed.

Severity: MEDIUM (Performance + UX)

Q12: THE CONCURRENT EVENT ORDERING PROBLEM
--------------------------------------------------------------------------------
File: backend/src/models/orm.py (ProcessEvent.timestamp)
File: backend/src/services/analytics.py (sorts by timestamp)
Research: inverbisanalytics.com, arxiv.org

Observation:
  ProcessEvent has a single `timestamp` field. Events are ordered by this 
  timestamp for variant calculation and DFG construction.

  Research on concurrent events notes:
  - Single timestamp = Activity completion time (no start time)
  - Identical timestamps require fallback ordering (alphabetical, row order)
  - True concurrency detection needs start + end timestamps

Question:
  When two events in a case have identical timestamps (common in batch 
  systems or coarse logging), what determines their order? Is it:
  - Database insertion order (non-deterministic)?
  - Alphabetical by activity name (arbitrary)?
  - A secondary sequence field (does not exist)?

  If ordering is arbitrary, the same log could produce different variants 
  depending on query execution plan. This is "Variant Drift."

Why This Matters:
  Conformance checking and DFG accuracy depend on correct event ordering. 
  A flipped order (A→B vs B→A) can change conformance results entirely.

Hypothesis:
  The system assumes timestamps are unique and ordered. This fails for 
  high-frequency systems. Solutions:
  - Add `sequence_number` field set during ingestion
  - Use secondary sort on a stable attribute (event ID)
  - Document the limitation for coarse-grained timestamps

Severity: HIGH (Analytical Accuracy)

Q13: THE LIFECYCLE CLASSIFIER ABSENCE
--------------------------------------------------------------------------------
File: backend/src/models/orm.py (ProcessEvent has no lifecycle field)
Research: inverbisanalytics.com (dual timestamps)

Observation:
  XES (the standard event log format) supports lifecycle transitions:
  - start: Activity began
  - complete: Activity finished
  - suspend/resume/etc.

  Our ProcessEvent model has no `lifecycle_transition` field. We only 
  store one timestamp per event.

Question:
  How do we distinguish "waiting time" (between activities) from "service 
  time" (activity duration)? Without start/complete timestamps:
  - Bottleneck analysis conflates queue time with work time
  - Resource utilization is unmeasurable
  - Parallel activity detection is impossible

Why This Matters:
  Process improvement requires knowing WHERE time is spent. If an activity 
  takes 10 hours between logs, is that:
  - 9h waiting in queue + 1h work? (Resource bottleneck)
  - 1h waiting + 9h work? (Activity complexity)

  Without lifecycle data, we're guessing.

Hypothesis:
  The schema was designed for the simplest case (one timestamp per event). 
  Supporting lifecycle transitions requires schema evolution:
  - Add `lifecycle_transition: enum`
  - Add `end_timestamp: Optional[datetime]`
  - Update ingestion to parse lifecycle from XES

Severity: HIGH (Feature Gap)

Q14: THE PM4PY CONVERSION OVERHEAD
--------------------------------------------------------------------------------
File: backend/src/services/mining.py (_to_pm4py_log method)
File: advanced_architectural_questions.txt ("THE OBJECT TAX")

Observation:
  Every mining operation follows this path:
  1. SQLAlchemy loads ORM objects (EventLog → Cases → Events)
  2. Python loops convert to List[Dict]
  3. PM4Py constructs its internal EventLog from the dictionaries
  4. PM4Py algorithm runs

  This is 3 data format conversions before any mining happens.

Question:
  What percentage of request latency is "conversion overhead" vs "actual 
  mining"? For a 1M event log:
  - Time to load from DB?
  - Time to convert to PM4Py?
  - Time to run Alpha/Heuristics miner?

  If conversion is >50% of time, we're optimizing the wrong thing. DuckDB's 
  Arrow tables could potentially feed PM4Py directly.

Why This Matters:
  DuckDB/Arrow research shows that zero-copy between analytical tools is 
  achievable. PM4Py explicitly supports Arrow input. We're not using it.

Hypothesis:
  The conversion was the "obvious" approach when integrating PM4Py. 
  Refactoring to Arrow-native would require:
  - Change ingestion to store Arrow/Parquet alongside ORM
  - Update mining service to read Arrow directly
  - Update PM4Py calls to use Arrow input

  This is significant work but could yield 10x speedup.

Severity: HIGH (Performance Debt)

CONCLUDING OBSERVATIONS
================================================================================

These 14 questions cluster into themes:

1. SCHEMA VS REALITY GAP
   - OCEL tables exist but aren't populated
   - AnalyticsCache exists but isn't used
   - RecommendationService exists but isn't exposed

2. IMPLICIT ASSUMPTIONS
   - Timestamps are unique (they're not)
   - Ingestion always succeeds atomically (it might not)
   - Frontend types match backend (hope-driven)

3. DEFERRED COMPLEXITY
   - Privacy controls (GDPR requirements)
   - Lifecycle semantics (dual timestamps)
   - Cache invalidation (stale data)

4. PERFORMANCE THEATER
   - DuckDB is fast, but we don't use its output
   - Arrow exists, but we convert to dicts
   - We claim speed improvements but pay conversion tax

RECOMMENDED ACTIONS:

1. AUDIT DEAD CODE
   - Verify AnalyticsCache usage or remove
   - Wire RecommendationService to API or mark experimental
   - Document OCEL ingestion path or remove OCEL2 tables

2. ADD EXPLICIT STATE
   - EventLog.status: PENDING | INGESTING | ACTIVE | FAILED
   - Guard analytics to only run on ACTIVE logs

3. ENFORCE CONTRACTS
   - Generate OpenAPI spec from Pydantic
   - Generate TypeScript from OpenAPI
   - CI fails on spec drift

4. PROFILE BEFORE OPTIMIZING
   - Measure conversion overhead vs algorithm time
   - Prioritize Arrow-native path if conversion dominates

5. PRIVACY BY DESIGN
   - Add pseudonymization option at ingestion
   - Support "aggregated mode" for analytics
   - Document GDPR considerations
